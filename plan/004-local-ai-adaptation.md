## 发现 1：依赖缺口（已修复）
后端 Ollama 集成依赖 `ollama` Python 包，但 pyproject 未声明 → `/api/ollama-models` 503 → 前端全部模型显示"未下载"。已 `uv add ollama`（0.6.3，pyproject +5 行 / uv.lock +15 行，官方源 URL 干净）。**绿包构建会自动带上。**

## 发现 2：上下文静默截断（部署级问题，已定位未修复）
- 实测：qwen2.5:1.5b 原生 32768，但 Ollama 默认以 **4096** 窗口服务（`ollama ps` 证实）；
- Octop Agent 提示词 ~20k（工具 12k+技能 3k+对话 4k）→ **~80% 被静默截断**，工具定义被切 → 模型把工具调用当文本输出、质量骤降（非 1.5b 参数量的锅）；
- UI"上下文使用 2%"双重失真：分母是 harness 兜底 128k（`DEFAULT_MAX_TOKENS`），分子是截断后上报值；
- 定性：Ollama 默认值是有意设计（内存保护）；**Octop 不配置/不提醒 num_ctx 是上游设计缺口**；
- 修复（配置级）：设 `OLLAMA_CONTEXT_LENGTH=32768`（环境变量或 Modelfile `num_ctx`），重启 Ollama 即可，无需改代码。

## 转化为部署规格
1. **vLLM 服务器（主形态）**：启动参数三条缺一不可——`--max-model-len 65536`（建议 ≥64k）、`--enable-auto-tool-choice`、`--tool-call-parser hermes`（Qwen 系；按所选模型调整）。不设后两条则 tool_calls 永远不返回（vLLM 接入第一坑）；vLLM 超限报 400 不静默截断，问题形态不同；
2. **单机 Ollama 版（如做）**：安装器预置上下文配置（环境变量或 Modelfile），用户无感；可加"上下文过小"预检；
3. **用户永远不需要碰环境变量**——配置责任在部署侧/安装包。

## 结论
**本地模型链路验证闭环**：Ollama 预设路径 ✅、自定义端点路径（vLLM 同路径）✅、工具调用协议 ✅、依赖缺口已修 ✅。Octop 侧对 vLLM 零改动接入成立；风险集中在服务端启动参数（已固化部署规格）。上游局限（harness 128k 兜底分母致 UI 百分比失真）记录不 patch。
